## Повторение оператором

`deploy/seed-pilot.mts` работает через API приложения при остановленном сервисе, не запускает доставку писем или ИИ. Существующие демо-входы использует из закрытого файла, чужие совпавшие ники без файла не перехватывает. Уже существующие объекты ищет перед созданием; изменённые/скрытые пользователем публикации не восстанавливает автоматически. Не удаляет старые данные. Повторный запуск без создания дубликатов ещё не проверен на сервере.

Публикуется только конкретный искусственный трек этого набора; роли модераторов и одобрение реальных пользовательских маршрутов не меняются. Это подготовка тестовой среды, не замена процесса модерации.

Из корня актуальной копии репозитория на сервере, под root, сначала сделать копию:

```sh
python3 deploy/backup.py create
systemctl is-active --quiet endurozone && (
  trap 'chown -R enduro:enduro /opt/endurozone/app/.data; systemctl start endurozone' EXIT
  systemctl stop endurozone && /opt/node-v24/bin/node apps/api/node_modules/tsx/dist/cli.mjs deploy/seed-pilot.mts
)
```

Проверять health после готовности сервиса, а не сразу после команды запуска. Конкретный прогон этого этапа использовал отдельные инструменты в `/opt/endurozone/ops`, рабочий коммит приложения не обновлялся.

Для локальной проверки набора в отдельной временной базе из корня проекта:

```sh
node apps/api/node_modules/tsx/dist/cli.mjs deploy/seed-pilot.mts --check
```

Проверка сохраняет временную базу и приватный файл в каталоге `ez-pilot-check-*` системной временной папки; не публиковать его. Эта проверка добавлена в CI. Успех локального прогона не равен проведённому пилоту с людьми.

Чтобы проверить наполненную восстановленную копию на сервере, выполнить `deploy/restore-check.mts` через tsx с путём отдельной базы и флагом `--pilot`. Разрешён только каталог `/var/backups/endurozone/restore-check-…/.data/postgres`. Скрипт использует закрытые демо-входы, проверяет данные и доступ, не выводит пароли.
