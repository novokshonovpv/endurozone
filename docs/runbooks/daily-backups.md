# Ежедневное резервирование Enduro.Zone

Настроено и проверено 10.10.2026 через консоль Timeweb. Платные настройки провайдера не менялись, новые услуги не подключались.

## Что работает

- `endurozone-backup.timer` включён; запускает копирование каждый день в **23:30 Europe/Moscow**. Часовой пояс указан в расписании независимо от системной зоны сервера.
- `endurozone-backup.service` создаёт закрытый архив PGlite через `/opt/endurozone/ops/backup.py`. На время копирования сайт ненадолго останавливается; ранее работающий сервис запускается обратно, в том числе после ошибки копирования.
- Пробный запуск службы завершился `Result=success`, `ExecMainStatus=0`; рабочий сервис после него активен, API отвечает 0.16.0.
- Первое запланированное срабатывание на момент проверки: **10 октября 2026, 23:30 МСК** (20:30 UTC). Срабатывание именно по расписанию ещё предстоит; проверен ручной запуск той же службы.
- Файлы закрыты для посторонних пользователей. Проверяются SHA-256 и читаемость архива. При свободном месте менее 256 МБ создание отклоняется до остановки сайта. SIGTERM вызывает выход с попыткой возобновления сервиса.
- Код копирования прошёл восемь локальных тестов, включая недостаток места без остановки приложения. Linux-проверка календаря и unit-файлов успешна на сервере.

При недоступности сервера в назначенное время `Persistent=true` запускает пропущенную задачу после возвращения таймера. Копирование отключается командой `systemctl disable --now endurozone-backup.timer`; существующие архивы при этом остаются. Не запускать обновление/наполнение базы одновременно с копированием.

## Уже существующее резервирование провайдера

В кабинете Timeweb для основного диска уже включены автоматические копии: ежедневно, начало окна с 00:15 МСК, одна сохраняемая копия, показанный тариф 300 ₽/месяц. Эти параметры только просмотрены. В списке на момент проверки показана копия от 9 октября, 03:11; наличие новой копии от 10 октября не подтверждено. Причина отсутствия более свежей копии не установлена.

Наш архив базы в 23:30 готовится до заявленного окна копирования диска. Это облегчает восстановление из завершённого архива, но не доказывает, что очередной бэкап провайдера действительно создан или что его полное восстановление проверено.

По [официальной документации Timeweb](https://timeweb.cloud/docs/cloud-servers/manage-servers/backup), копии панели не защищают от всех программных/аппаратных сбоев и удаления сервера; провайдер рекомендует дополнительные удалённые копии. Поэтому **независимое удалённое резервирование ещё не настроено**. Восстановление всего диска также не выполнялось: оно затронуло бы другие сайты сервера.

## Контроль оператором

```sh
systemctl list-timers endurozone-backup.timer --no-pager --full
systemctl show endurozone-backup.service -p Result -p ExecMainStatus
journalctl -u endurozone-backup.service -n 20 --no-pager
df -h /var/backups/endurozone
```

Не публиковать журналы с приватными ссылками/письмами. Автоудаление архивов, срок хранения, уведомление об ошибках и независимое хранилище пока не настроены. Следить за свободным местом; проверка 256 МБ не заменяет управление объёмом копий. При сбое выполнить проверку состояния сайта и устранить причину перед новым запуском.

Сначала выбрать отдельное хранилище и согласовать доступы, стоимость и срок хранения. Затем настроить шифрование/доставку и восстановить копию именно из этого хранилища. Для содержимого базы уже выполнено восстановление синтетического набора по [отчёту](pilot-data.md); результат не следует переносить на ещё не проверенный внешний канал хранения.
