# Совместная работа: Смоленск — Сочи

Версия 0.2 • 10.10.2026. Это готовый порядок работы для двух основателей; внешние аккаунты, приглашения и репозиторий пока не созданы.

## Роли и решения

| Направление | Ответственный | Кто проверяет |
|---|---|---|
| Ценность продукта, интервью, приоритеты, бренд | Вы | Друг и пилотные участники |
| Сайт, пользовательские сценарии, контент | Вы | Друг по интеграции, участники по понятности |
| Сервер, API, база, доступы, импорт, платежный контур | Друг | Вы по бизнес-сценариям |
| iOS / Android, карта на устройствах, push | Друг | Вы на своих устройствах, пилот |
| Сообщество, магазины, тренеры, модерация | Вы | Друг по средствам управления |
| Безопасность, резервные копии, выпуск | Друг | Вы подтверждаете готовность сценариев |
| Расходы, доли, договоры, изменения большого объёма | Совместно | Зафиксированное решение обоих |

Вы отвечаете за «всё остальное», но это не означает, что все задачи нужно делать лично: юридическую проверку, бухгалтерию и узкую экспертизу можно заказать точечно. Возможность разработки сайта уточняется по вашим навыкам; при необходимости первый интерфейс строится из простого готового набора компонентов.

## Общая рабочая среда

Рекомендуемый минимальный набор: **один приватный GitHub-репозиторий и GitHub Projects**, общие документы в репозитории, общий чат и видеосвязь. Если доступность сервиса или хранение данных не устраивает, используйте один GitLab / Gitea с аналогичным процессом; не размазывайте задачи между несколькими досками.

1. Создать организацию проекта, добавить оба личных аккаунта и включить двухфакторный вход. Хранилище исходников не должно содержать реальные персональные данные райдеров.
2. Создать приватный репозиторий с общими папками `apps/web`, `apps/mobile`, `apps/api`, `packages/contracts`, `docs`, `infra`. Технологии сначала согласуются с другом.
3. В доске создать статусы: «Идеи», «Готово к работе», «В работе», «Проверка», «Готово».
4. На задаче хранить: проблему, результат, критерии приёмки, одного владельца, приоритет, оценку, зависимость и ссылку на макет / изменение.
5. В работе держать максимум одну крупную задачу на человека. Оценивать небольшие куски на 1–3 рабочих дня, а не «сделать весь магазин».
6. Документы: `docs/product.md`, `docs/api`, `docs/decisions`, `docs/runbooks`, `docs/research`. Каждый результат интервью содержит дату, тип участника и вывод; контакты хранить отдельно с ограниченным доступом.
7. Пароли и ключи — в общем менеджере паролей с отдельными личными доступами. В репозитории только образцы переменных без секретов.
8. Создать адрес для обращений проекта после выбора домена, разделить права администратора, модератора и продавца.

## Как работать без ожидания друг друга

- Друг сначала публикует согласованный контракт API и тестовые примеры. Вы делаете сайт на этих примерах до готовности сервера.
- Единые описания полей и ошибок лежат в `packages/contracts` и OpenAPI. Изменение контракта обсуждается до объединения кода.
- На сервере и на клиенте одна логика состояния «совместимость неизвестна», одна шкала сложности и одинаковые коды статусов заявки.
- Для мобильного клиента используем тот же API; мобильные экраны не диктуют отдельную модель данных.
- Каждое изменение выполняется в своей короткой ветке и проходит просмотр вторым основателем. Защищаем основную ветку от случайной прямой записи.
- На тестовом окружении только синтетические данные. Промышленное окружение и его доступы отделены.

## Ритм

Оба города находятся в одном часовом поясе. Предлагаемый ритм, который нужно подтвердить по вашим графикам:

- Понедельник, 30 минут: цель недели, 2–4 задачи, зависимости и доступный объём времени.
- Каждый рабочий день: короткое сообщение «сделал / дальше / что мешает». Обязательной ежедневной встречи нет.
- Среда, 20 минут: только нерешённые вопросы по API, данным и партнёрам.
- Пятница, 45 минут: показать работающий сценарий, проверить по критериям, разобрать обратную связь.
- Раз в две недели: спринт и пересмотр объёма. Раз в месяц: деньги, метрики, партнёры, следующий этап.

Не создавать эти встречи автоматически без согласованного времени. Важные решения после звонка фиксируются письменно, чтобы их не искать в чате.

## Что значит «задача готова»

Есть работающий сценарий, проверен основной и ошибочный путь, интерфейс работает на телефоне, права доступа проверены на сервере, нет секретов и реальных данных в исходниках, документированы изменения API, второй основатель посмотрел результат. Для операций с оплатой, геоданными, доступами и совместимостью обязательны содержательные проверки.

Для маленьких текстовых и визуальных изменений достаточно просмотра. Не требовать формальных тестов, которые только повторяют реализацию.

## Договорённости между основателями до первого большого вложения

Записать и подписать подходящее соглашение после выбора формы бизнеса. Это перечень вопросов, а не готовый юридический договор:

1. Доли, вклад деньгами и временем, порядок их изменения; не считать автоматически 50/50.
2. Кому принадлежат код, бренд, домен, каталоги и материалы; как оформляются права на результат подрядчиков.
3. Кто утверждает расходы и какой предел может оплатить самостоятельно.
4. Что происходит при временном отсутствии, выходе, продаже доли, споре или прекращении проекта.
5. Как принимаются решения при разногласии двух участников.
6. У кого доступны домен, хостинг, база, магазинные аккаунты приложений и резервные копии; как восстановить работу при потере доступа.
7. Как учитывается прибыль, зарплата и возмещение личных расходов.

## Две пилотные территории

Город полезен для тестирования на местах, а не для разделения продукта на два сервиса. Каждая сторона собирает местных райдеров, тренеров, магазины и авторов треков. Технический владелец может проверять сервер, а второй — сценарий пользователя. Региональные проверки подключаются к общим задачам.

В Смоленске проверяем один локальный сценарий и подходящие сезонные условия; в Сочи — тот же сценарий с другим рельефом и условиями. Не пытаемся вручную заполнить всю Россию до проверки двух регионов.
