# Техническое задание 0.2

10.10.2026 • Enduro.Zone • Для обсуждения с другом, который отвечает за backend и мобильные приложения.

## Архитектура

На старте — один модульный сервер, одна основная БД, общий API и отдельные клиенты. Микросервисы и отдельные команды для каждого раздела сейчас увеличат сложность.

```text
Адаптивный сайт / будущая PWA ─┐
iOS и Android ────────────────┼─ API → модули продукта
Кабинет модератора / продавца ┘          │
                         PostgreSQL + PostGIS
                         Хранилище фото / GPX / материалов
                         Фоновые задания: импорт, уведомления
                         Поиск по знаниям → шлюз ИИ
```

Предлагаемый набор: TypeScript; сайт React / Next.js; mobile React Native; сервер на знакомом другу фреймворке; PostgreSQL + PostGIS; совместимое с S3 хранилище в РФ; первоначально поиск средствами PostgreSQL; Redis и отдельный поиск только при измеренной необходимости. Если друг уже уверенно работает с другим стеком, сохраняем общий API и требования, а технологии меняем.

Сайт и приложения разделяют контракты, типы и часть бизнес-логики. Все экраны автоматически общими не становятся. Карта: MapLibre для отображения, лицензированные данные и тайлы с условиями, подходящими для России и будущего офлайн-доступа. Проверить на устройствах до окончательного выбора библиотеки.

Демонстрационный Sites-проект является отдельным статическим прототипом. Его источник не представляет промышленный backend и не определяет размещение персональных данных рабочего сервиса.

## Границы модулей и пример API

- `/auth`, `/me`, `/profiles` — регистрация, сессии, настройки, выгрузка / удаление данных.
- `/bike-variants`, `/me/bikes`, `/bikes/{id}/posts` — справочники и журнал.
- `/feed`, `/posts`, `/comments`, `/follows` — сообщество.
- `/locations`, `/tracks`, `/tracks/{id}/revisions`, `/reports` — карта, bbox и поиск рядом.
- `/rides`, `/rides/{id}/requests`, `/rides/{id}/participants` — события и заявки.
- `/catalog/products?bike_variant_id=…`, `/offers`, `/seller/imports` — товары и совместимость.
- `/orders`, `/payments/webhook`, `/returns` — торговый этап.
- `/schools`, `/courses`, `/bookings` — обучение.
- `/mechanic/conversations`, `/mechanic/messages` — зарегистрированный пользователь, проверка квоты и контекста на сервере.
- `/admin/moderation`, `/admin/fitments` — управление с отдельными правами.

Это группы контрактов, не обещание уже существующих endpoints. Для каждого согласовать метод, схему запроса / ответа, пагинацию, ошибки и права. Для загрузок — ограничение размера, проверка содержимого и безопасная обработка файлов.

## Совместимость деталей: правило принятия решения

1. Определить точную версию мотоцикла. Неполный профиль → запросить уточнение.
2. Проверить изменения компонентов. Деталь к изменённому узлу не подбирается по заводской версии без дополнительных параметров.
3. Найти связь в Fitment с источником и ограничениями.
4. Не объединять заявление продавца и подтверждение каталога в один зелёный значок.
5. Если связь отсутствует, показывать «данных недостаточно» и способ уточнить OEM / размеры. Не скрывать это состояние фильтром «всё подходит».
6. Зафиксировать, какую версию данных видел покупатель, в будущем заказе.

Пилотные проверки: совпадающая версия; соседний год с несовместимостью; другая модификация; изменённые колёса; универсальная деталь без размеров; конфликт двух источников; просроченный остаток; повторный импорт одного файла.

## Поиск рядом и приватность треков

- Поиск расстояния выполнять по координатам с корректной системой координат и единицами, используя пространственный индекс.
- Если разрешение GPS отклонено, остаётся выбор города / области на карте.
- Город профиля и разовая точка поиска — разные поля. Не записывать разовую точку в публичный профиль.
- Скрытие концов трека формирует новую публичную геометрию; закрытые точки не возвращаются публичным API и не остаются в доступном оригинале.
- Все права проверять на сервере, включая прямой URL, GPX и вложения. Кнопка скрытия в интерфейсе не обеспечивает приватность.
- Офлайн-карту строить только по разрешению поставщика данных. Публичные тайлы OpenStreetMap нельзя скачивать массово для офлайн-пакетов.
- Сохранение GPX ≠ полноценная навигация; сначала обмен треками, затем запись и офлайн-карта, позднее указания поворотов при подтверждённом качестве.

## ИИ-механик: реализация и качество

Сначала небольшой набор законно используемых документов по пилотным версиям. Поиск по документам с фильтром версии мотоцикла, затем ответ модели с цитированием. Нормализованный артикул / применимость берётся из каталога, не извлекается как окончательный факт из свободного ответа.

Серверный шлюз отделяет ИИ-провайдера от продукта, ограничивает стоимость, время запроса, число попыток и объём контекста. Персональные контакты и координаты удаляются из контекста. ИИ не имеет полномочий оплаты или произвольной записи в БД; в интерфейсе пользователь подтверждает черновик.

До беты собрать 50 проверенных вопросов: уход, интервалы, отсутствующие данные, разные годы и версии, критичные симптомы, ложные сведения в загруженном материале. Друг и привлечённый механик проверяют фактическую опору на источники и корректные границы ответа. Для точных опасных числовых инструкций без нужного источника должен следовать отказ от выдачи числа, а не правдоподобная догадка.

## Безопасность и надёжность

Личные сессии, безопасное хранение паролей / внешнего входа, права на сервере, ограничения запросов, защита от спама, очистка опубликованного содержания, журнал важных изменений без секретов. Для администратора — дополнительная защита входа.

Резервное копирование БД и файлов, тест восстановления до пилота. Начальные цели для пилота: потеря данных при аварии не более 24 часов, восстановление в пределах рабочего дня; стоимость и возможность более строгих целей согласовать отдельно.

Для заказа — неизменяемый снимок цены и условий; идемпотентность создания заказа и обработки платёжных уведомлений, проверка подписи и суммы, корректная обработка отмены, повторного webhook и возврата. Конкурентное вступление в последнюю доступную позицию поездки обрабатывается транзакционно.

Удаление аккаунта и контента учитывать в БД, файлах, поисковых индексах и резервных копиях по утверждённой политике. У торговых документов отдельные основания и сроки хранения.

## Критерии готовности релизов

### Ядро сайта

- Участник создаёт аккаунт и мотоцикл, публикует запись; другой комментирует и подписывается.
- Отправленный трек сначала черновик / модерация; администратор публикует, отклоняет и обрабатывает жалобу.
- Подходящее событие находится по региону и уровню; лимит не переполняется, отмена уведомляет участников.
- Приватная запись и закрытый трек недоступны чужой сессии и через прямой URL.
- Работает отказ GPS, медленная сеть, мобильная ширина и восстановление резервной копии.

### Каталог и механик

- Импорт не дублирует позиции; ошибочные записи показываются отдельно, прежние данные не уничтожаются.
- Точная версия, другой год и отсутствие применимости дают разные результаты.
- Механик использует документы нужной версии, сообщает о нехватке источника и не создаёт заказ самостоятельно.

### Маркетплейс

- Заказ проходит оплату, отказ оплаты, повторное уведомление, отмену, доставку и возврат.
- Не возникает повторного списания / заказа от повторного запроса.
- Покупатель видит продавца, полную цену, доставку и правила возврата; юридическая модель и процессы поддержки утверждены.

### Мобильные приложения

- Используется общий аккаунт и API; история и изменения синхронизируются на сервере.
- Отказ / ограничение геолокации и уведомлений не блокирует базовый сценарий.
- Разрешённые офлайн-данные открываются без сети; изменение треков при возвращении сети не теряется.
- Проверены энергорасход записи GPS, фоновые ограничения, реальные iPhone / Android и способы сборки / публикации.
- Подготовлены политика приватности, описание используемых разрешений, удаление аккаунта и проверка правил продажи цифрового обучения.
